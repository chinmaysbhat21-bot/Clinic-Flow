# Backend readiness audit

Phase 8 can be reviewed and published independently of Jay’s frontend. The browser integration belongs to Phase 9. Production deployment is a separate decision.

| Capability | Current evidence | Before rollout |
|---|---|---|
| Google OAuth renewal | The adapter now supports a server-side refresh grant, an access token cache and concurrent refresh deduplication per process. Existing calendar operations were verified in Phase 5; renewal is verified with fixtures. | Configure the existing OAuth client and test a real read-only availability request. Plan refresh token replacement for Testing-mode grants and revocation. Use secure secret storage for deployment. |
| SMS OTP | Local console delivery is explicitly development-only. Expiry, resend, retry and single-use checks are tested. | Approve a provider and sender configuration. Test provider timeouts and retries, abuse limits and delivery without exposing codes. |
| SMS, email and WhatsApp notifications | Brevo Free email reuses the durable outbox and consent checks. Read-only provider checks confirmed a Free plan, an enabled transactional relay and an active matching sender. Fixtures cover the persistent 250-attempt cap and ambiguous submissions. SMS and WhatsApp are simulated. | Approve one fictional email to an approved inbox. Confirm API acceptance and check Brevo logs and inbox receipt. Patient mailbox ownership and automatic delivery updates remain prerequisites for broader rollout. See the [notification setup](NOTIFICATION_SETUP.md). |
| English, Kannada and Hindi templates | Static subjects and bodies use the saved language with English fallback, clinic-local appointment times and verified INR amounts. Fixtures exercise all supported events and Unicode Brevo payloads. | Review Kannada and Hindi wording with fluent speakers. Localized inbox rendering remains unverified. |
| Razorpay webhook delivery | Signed raw-body payment, order and refund handlers are tested with fixtures, including durable acknowledgement before provider lookup, restart recovery, lease expiry and concurrent duplicates. Manual public ingress checks passed. A captured ₹500 Test Mode payment was verified and recovered via API polling; Razorpay-originated delivery remains unverified. | Approve an HTTPS ingress forwarding only the signed webhook route. Verify external delivery and retries without exposing admin or OTP endpoints. See the [webhook setup](RAZORPAY_WEBHOOK_SETUP.md). |
| Deployment | The API binds to loopback, uses SQLite and starts durable workers. Local type checks and fixture tests cover core flows. | Define hosting, HTTPS and ingress, shared storage and backup/restore, migration rollout, secret rotation, readiness probes, monitoring and coordinated login throttling. Run a staging smoke test before production. |
