# Google Calendar demo verification

Use the existing Clinic Flow Test project and dedicated Google test account. Use calendars containing only fictional appointments.

1. In Google Cloud, select the **Clinic Flow** project. Confirm **Google Calendar API** is enabled. For an External app in Testing, confirm the dedicated account is listed as a test user.
2. Reuse the existing **Web application** OAuth client. Add `https://developers.google.com/oauthplayground` to its authorized redirect URIs only if missing. Create a web client in this same project only if there is no suitable existing client. In the [OAuth Playground](https://developers.google.com/oauthplayground), select **Use your own OAuth credentials**, choose **Offline** access and the consent prompt, enter that client’s credentials, and authorize these scopes with the dedicated account:
   - `https://www.googleapis.com/auth/calendar.events`
   - `https://www.googleapis.com/auth/calendar.events.freebusy`
3. Exchange the authorization code for tokens. Put the client ID, client secret and refresh token directly in `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` and `GOOGLE_OAUTH_REFRESH_TOKEN` in the local Git-ignored `.env`. Do not share them in chat or logs. Renewal takes precedence when all three values are set. For the older static-token workflow, leave all three blank and use `GOOGLE_ACCESS_TOKEN`.
4. In Google Calendar, create a secondary calendar named **Harbor Booking Test**. Set its time zone to Asia/Kolkata to match seeded Harbor. The OAuth account must own the calendar or have **Make changes to events** permission if another account owns it. In calendar settings under **Integrate calendar**, copy its Calendar ID and configure `GOOGLE_CALENDARS_JSON={"harbor":"<calendar-id>"}` in the local `.env`. Use one distinct test calendar per configured clinic. The legacy `GOOGLE_CALENDAR_ID` fallback applies only to Harbor when the map is unset.
5. Start the API with `npm.cmd run dev`. Use the Harbor clinic and fictional booking details, then verify that a busy interval disappears from availability. When a separately authorized Test Mode booking is available, confirm, move, and cancel it through the normal booking APIs and inspect the dedicated calendar. The health flag reports configuration presence rather than OAuth validity.

Google documents the [OAuth Playground flow](https://developers.google.com/admob/api/v1/how-tos/playground), [free/busy scopes](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query), [event scopes and fields](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), and [calendar sharing permissions](https://developers.google.com/workspace/calendar/api/concepts/sharing).

After updating the environment, restart the API once and request Harbor availability to verify renewal without writing to Google Calendar. The API retrieves and caches access tokens on demand, renews shortly before expiry, and retries once on an explicit Calendar 401. An ambiguous provider write remains subject to reconciliation.

External Google apps in Testing normally receive seven-day refresh tokens for these Calendar scopes. Tokens may also be revoked. If the API returns `GOOGLE_OAUTH_REAUTH_REQUIRED`, check the client credentials, reauthorize in Playground and replace the refresh token. Using your own OAuth client avoids Playground's separate default 24-hour revocation policy. [Token expiration](https://developers.google.com/identity/protocols/oauth2#expiration) · [Google refresh flow](https://developers.google.com/identity/protocols/oauth2/web-server#offline)

The backend stores appointment times as UTC instants and computes working hours in the clinic time zone. A Google clinic has one calendar and one concurrent booking capacity across its doctors. Calendar events have a generic title, an opaque hold reference, and a doctor identifier for recovery. They contain no patient contact information, medical details or attendees.

Calendar reads and writes are covered by deterministic provider fixtures. Actual OAuth and Google API verification await the dedicated credentials and calendar. Google Calendar cannot atomically lock a slot against an external editor. The API checks availability before writes and uses event ETags when supplied for changes. Restrict calendar edits during the demo. A missing, forbidden or inconclusive event lookup leaves any unresolved operation under the existing retry and manual review rules; only a known event and matching evidence can resolve it automatically. A deleted-event record may disappear before reconciliation, requiring manual review. Legacy events without doctor metadata can also require review.
